# Ripster

An on-device media downloader. Paste a link and Ripster works out what it points to:

- an **HLS stream** (`.m3u8`): choose a quality, download it, and get a standalone MP4;
- a **direct media file** (MP4, MKV, WebM): download it and keep it as is;
- a **web page**: Ripster reads the media links the page openly declares (video elements, Open
  Graph, schema.org) and uses the first one that passes the same checks as a pasted link.

Everything happens on the device: no backend, and no media is uploaded anywhere for processing.
Downloads run in the background, survive app restarts, resume after network loss, and can be
cancelled or retried from the queue.

Ripster is a Kotlin Multiplatform (KMP) project with Compose Multiplatform UI. Android is the
first and currently only implemented platform; the shared code is kept free of Android types so
an iOS app can be added later.

> Only download media you're allowed to download. Ripster never runs page scripts, never reads a
> site player's private configuration, and never bypasses DRM, sign-in, age verification or
> other access restrictions. A page that doesn't openly provide a downloadable source is reported
> as such, not worked around.

## Requirements

- Android Studio (or the Android SDK command-line tools) with API level 37 installed.
- JDK 17 or newer to start Gradle. The Gradle daemon itself runs on JDK 21
  (`gradle/gradle-daemon-jvm.properties`), which Gradle downloads automatically if missing.
- An Android device or emulator running Android 9 (API 28) or newer.

## Build, run and test

```bash
# Debug APK: androidApp/build/outputs/apk/debug/androidApp-debug.apk
./gradlew :androidApp:assembleDebug

# Build and install on the connected device
./gradlew :androidApp:installDebug

# Unit tests (commonTest and androidHostTest, on the local JVM; no device needed)
./gradlew :shared:testAndroidHostTest

# Android lint
./gradlew :androidApp:lint
```

The sample-stream picker is only shown in debug builds. Debug builds install as
`in.geekofia.ripster.debug` ("Ripster Debug"), next to a release build.

## Versions and release builds

The version lives in `version.properties` (`VERSION_NAME` in SemVer, `VERSION_CODE` as an
integer). Change it with the script rather than by hand:

```bash
scripts/bump-version.sh patch            # or: major | minor | build | set X.Y.Z
scripts/bump-version.sh minor --dry-run  # show the change without writing it
```

Release builds are minified with R8. To sign them, copy `keystore.properties.example` to
`keystore.properties` (git-ignored) and fill it in; without it, release builds are unsigned.

```bash
./gradlew :androidApp:assembleRelease   # APK
./gradlew :androidApp:bundleRelease     # AAB for Play
```

Every build also copies its outputs to `androidApp/build/dist/` with readable names and prints
their paths, e.g. `Ripster-v0.1.0-1-release.apk`, `Ripster-v0.1.0-1-release.aab` and
`Ripster-v0.1.0-1-release-mapping.txt` (R8's mapping, to read release stack traces).

## Architecture

Two Gradle modules, as generated by the KMP template: `:shared` holds almost everything, and
`:androidApp` is a thin host (`RipsterApplication`, `MainActivity`, manifest, launcher icon).
Conventions follow the sibling MorseKit project: manual dependency injection through one
`AppContainer`, platform capabilities behind interfaces in a `PlatformServices` bag, a Route +
ViewModel + stateless Screen per feature, and repositories that expose `StateFlow`.

```text
paste a link
  └─ DefaultSourceResolver ─────────────── core/source (shared)
       0. site adapters (core/source/site), only for their own exact domains
       1. direct file: 64-byte range probe, container from its first bytes
       2. HLS manifest: fetch, parse, pick variants
       3. web page: declared media links, each re-checked as 1 or 2
  └─ ResolvedSource ──▶ Download screen: details, quality, output, Download
  └─ DownloadCoordinator ────────────────── core/download (shared)
       queue state machine, persisted queue, reconciliation with the engine
  └─ DownloadEngine (Media3 DownloadManager + DownloadService) ─ androidMain
  └─ MediaExporter: Transformer remux to MP4, or a byte-exact copy ─ androidMain
  └─ OutputPublisher: app storage or a folder chosen with SAF ── androidMain
```

### Shared code (`shared/src/commonMain`)

| Package | Contents |
| --- | --- |
| `core/source` | URL rules (`SourceUrl`), typed errors (`MediaError`), resolvers, page reading (`PageMediaExtractor`), file sniffing, sample streams |
| `core/source/site` | The `SiteAdapter` contract and one adapter (see *Supported sources*) |
| `core/hls` | A portable M3U8 parser: variants, audio renditions, duration, encryption, live detection |
| `core/download` | Job model, pure state transitions, the versioned queue codec, `DownloadRepository`, `DownloadCoordinator`, the engine contract |
| `core/export` | The exporter contract, export outlook per codec, safe file names |
| `feature/home`, `feature/queue` | The two screens and their ViewModels |
| `platform` | Interfaces the platform implements: HTTP, storage, clipboard, file actions, folder picker |

### Android code (`shared/src/androidMain`)

| Package | Contents |
| --- | --- |
| `download` | Media3 `DownloadManager` (per-job cache keys), `RipsterDownloadService` (foreground, `dataSync`), request building with HLS stream keys, error mapping |
| `export` | `TransformerExporter`, `ExportService` (keeps exports alive in the background), `OutputPublisher` |
| `platform` | `HttpURLConnection` client with validated redirects, atomic queue file, SAF and permission bridge, FileProvider sharing |

### How a download stays reliable

- **Queue states:** Queued → Resolving → Downloading → Exporting → Completed, or Failed /
  Cancelled. Transitions are a pure function; once a job is finished, late engine updates are
  ignored, so a cancelled job can't come back as completed.
- **Reconciliation, not events:** the engine publishes a versioned snapshot of every download,
  and the coordinator compares each job against it under a lock. The same path handles a fresh
  download, a slow observer and recovery after the process was killed.
- **Persistence:** the queue is saved atomically (only state changes, not progress ticks), and
  Media3 keeps its own download index, so downloads resume where they stopped.
- **Retry:** re-inspects the link (an expired link fails fast) and resumes the download, or goes
  straight to export when the media is already on the device. Unsupported sources aren't retried.
- **Isolation:** each job's cached data is keyed by its id, so two jobs for the same link never
  share data, and data that has gone missing is downloaded again instead of failing forever.

## Supported sources

| Input | What Ripster does | Output |
| --- | --- | --- |
| HLS master or media playlist (`.m3u8`, VOD) | Lists variants (resolution, frame rate, bitrate, codecs) with the matching audio; downloads only the chosen one | MP4, remuxed without re-encoding when the codecs allow (H.264/H.265 + AAC) |
| Direct MP4, MKV or WebM file | Recognised from its first bytes, not its name or content type; size used for the storage check | The original file, unchanged |
| Web page | Reads `<video>`/`<source>`, Open Graph `og:video*` and schema.org `VideoObject` links; HLS preferred, then files; up to 3 tried | As above |
| A page on a site with an adapter | The adapter reads the page's public metadata (title, thumbnail, duration, canonical URL) and offers a download only for a link the page openly declares that passes the checks above | As above, or a typed reason why there is nothing to download |

Rejected, each with its own message: plain `http`, URLs with credentials, live streams, DRM and
SAMPLE-AES encryption, pages that declare nothing usable, HTTP errors (expired links are told
apart from denied access when the URL is signed), and too little free space (about twice the
download plus 50 MB is needed while it's being saved). Clear-key AES-128 HLS is supported.

### Site adapters

There is one, for Pornhub watch pages (`view_video.php?viewkey=…` on `pornhub.com` /
`pornhub.org`, with exact-domain matching so lookalike hosts aren't claimed). Its outcomes are
typed: *resolved*, *metadata only* (the page provides no openly declared source), *unsupported*,
*restricted* (access denied, sign-in or age verification, which are never bypassed),
*unavailable* and *network error*. Only *resolved* can start a download. Further sites can be
added as another `SiteAdapter` without touching the rest.

## What has been tested

On a physical device (Android 16, API 36):

- **Big Buck Bunny**: downloaded and exported to a 488 MB 1080p MP4. Verified on a computer with
  `ffprobe` (H.264 1920×1080 + AAC, 634.6 s, matching the playlist) and a full `ffmpeg` decode
  without errors. Recovery was exercised too: after a crash mid-export, the export restarted on
  its own at the next launch.
- **Apple BipBop** and **Tears of Steel**: downloaded and exported successfully, and parallel
  downloads worked (tested by hand on the device).
- **A direct MP4 found on a web page** (a fragmented MP4, 2560×1440): downloaded and saved; the
  saved file is byte-identical to the download (SHA-256) and decodes fully.

By unit tests only (138 tests in `commonTest` and `androidHostTest`, run on the JVM):

- URL rules, the M3U8 parser, page reading and metadata fallbacks, file sniffing, the queue
  codec (including old formats), state transitions, error messages;
- the resolvers with a fake network, including web pages and the site adapter (synthetic HTML
  fixtures; no live sites are contacted);
- the coordinator with a fake engine and exporter: cancellation races, retry, recovery after
  process death, storage checks, data isolation, and that unresolved sources never reach the
  download engine.

Not yet tested on a device: exporting an AC-3 / E-AC-3 BipBop variant, MKV and WebM files,
choosing a SAF output folder, and the minified release build (it's unsigned without a keystore).

## Known limitations

- **HLS:** VOD only; live and event playlists are refused. Export needs codecs the device can
  handle: H.264/H.265 + AAC remux cleanly, while AC-3 / E-AC-3 audio needs a decoder many phones
  lack, so those variants may fail with "Can't export to MP4" (shown as a warning before download).
- **Direct files** are kept in their own container: MKV is not converted to MP4. Their duration is
  only known after download. If a server ignores range requests, the size can be missing and the
  storage check is skipped (a full disk is still reported by the engine).
- **Web pages:** only links a page declares in standard places are used. Pages whose player builds
  stream URLs in scripts are reported as having no downloadable source.
- **Requests:** no custom headers, cookies or sign-in; a field is reserved in the queue format.
- **Background work:** downloads run in Media3's foreground service. Android may refuse to start
  the export service from the background; the export then continues in the app process without
  that protection, and restarts after the next launch if the process is killed.
- **Concurrency:** at most 2 downloads at once and one export at a time.
- **UI:** thumbnails are read but not displayed (that needs an image-loading library).
- **Platforms:** Android only. The template has no iOS target yet.
